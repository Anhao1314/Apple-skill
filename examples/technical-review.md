# 技术方案评审示例

材料和产品均为虚构。输出由维护者手写，仅示范格式与取舍，不是 Agent 实测记录。安装时保留完整目录；无需额外文件。

## 完整输入（复制调用）

```text
请用 apple-product-design 评审以下虚构 RFC，不写代码。
任务：内网操作员用 CLI 将本地 CSV 转为审核记录。
约束：完全离线；已有 Node.js；禁止 SaaS 和远程模型；两名维护者。
必须保留：操作身份、记录可追溯、数据保留策略、原始文件不被改写。
候选方案：单进程 CLI，或微服务+消息队列+远程日志；预先设计通用十种导入插件。
已知：目前只有一种 CSV；文件大小、失败重试、身份来源和保留期限未知。
请给技术取舍、最小方案与待确认项；不要因低频删掉审计。
```

## 示范输出

总判断：先采用离线单进程 CLI；保留审计与数据保留要求。远程日志违反环境约束。

| 项目 | 决策 | 理由 |
| --- | --- | --- |
| Node.js CLI | 保留 | 使用已有运行时，部署面较小 |
| 微服务与队列 | 暂缓 | 未见吞吐或隔离要求；增加离线维护负担 |
| 远程日志 | 删除 | 违反完全离线要求 |
| 十种导入插件 | 暂缓通用框架 | 仅一种格式；重复次数只是提醒，有确定扩展需求时可提前抽象 |
| 身份与追溯记录 | 必须保留 | 用户明确要求，不按频率删减 |

最小方案：本地读取与校验 → 生成审核记录及处理状态 → 写入按已确认保留策略管理的本地存储；保留原文件。失败不给成功提示，重试规则与重复记录识别需明确。
假设：现有身份机制能在离线环境提供操作身份；操作系统用户名是否足够尚未确认。
关键问题：最大文件规模、身份可信要求、保留期限和删除责任。它们会改变处理与存储设计，先不承诺工期或具体安全实现。
下一步：用脱敏小样本验证成功、非法 CSV、写入失败、重复执行和原文件完整性；大文件策略待规模确认后评估。此处是建议验证计划，没有实际运行记录。
