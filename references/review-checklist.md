# 产品评审清单（Review Checklist）

> 模式一评审时逐项过；每项给出 通过 / 存疑 / 不通过 的判定与证据。存疑和不通过项进入报告；轻量评审只使用相关部分，无组织材料时跳过组织项。证据不足标待验证，不虚构访谈。括号内标注对应原则编号（见 principles.md）。

## Step 1 本质定义

- [ ] 能用一句无参数、有画面的用户语言说清产品是什么、给谁、解决什么任务。
- [ ] 遮住产品名，定义不会与任意竞品互换。
- [ ] 团队/材料中对产品的表述彼此一致，没有"官方定义 vs 实际做的事"两张皮。
- [ ] 每个现存功能都能回链到这句话；回链不上的已列入待砍清单。
- [ ] 定义描述的是用户任务/结果，而非技术实现、功能列表或公司战略。

**红旗**：定义句出现"一站式、全方位、赋能、平台、生态、闭环"等抽象词且无法翻译成具体场景；一句话超过 30 字仍说不清；不同人给出不同定义。

## Step 2 功能减法

对功能清单中**每一项**填写判定：

| 功能 | 服务的核心任务 | 删除影响（具体场景） | 判定 | 理由 |
|---|---|---|---|---|
| | | | 保留强化/合并/下沉/删除 | |

判定问题：
- [ ] 删除后哪些用户与任务受影响？没有数据不编造比例；低频但必要的合规、安全、无障碍能力保留。
- [ ] 是否存在两个功能可合并为一个更通用的能力？
- [ ] 低频功能是否已下沉二级，且需要时能被自然发现（不是藏到找不到）？
- [ ] 每个功能的存在理由是"具体用户场景"，而非"竞品有 / 老板要 / 以后可能 / 技术上能做"？
- [ ] 被简化掉的复杂度是真消除/自动化了，还是转嫁给了用户？
- [ ] 是否有显式的 not-doing list，并写清每个"不做"顶住了什么诱惑？
- [ ] 近三个版本新增与删除的数量级是否失衡（只加不减）？

**红旗**：功能优先级由"谁声音大"决定；核心路径并列能力缺少共同主线（数量不是硬阈值）；任何功能都讲得出重要性但产品整体讲不出主线。

## Step 3 体验倒推

- [ ] 已写出理想体验故事线（用户视角逐拍），并与现状路径逐拍对照。
- [ ] 每个妥协点标注了成因：技术约束 / 成本 / 组织分工 / 商业指标 / 历史包袱。
- [ ] 每个技术选型能对应到具体体验收益，对应不上的标记为技术自嗨。
- [ ] 对最伤体验的妥协点，至少给出一个替代路径（自研/换方案/砍范围/等待技术）。
- [ ] 没有让用户为系统架构买单（如让用户理解同步逻辑、手动刷新、自己拼接数据）。

**红旗**：产品流程直接映射内部系统模块或数据库表结构；出现"因为我们的架构只能这样"且无人挑战；演示路径全是 happy path。

## Step 4 端到端链条

画出链条并逐环标注控制状态：

| 链条环节 | 控制状态（自控/合作/不可控） | 失败表现 | 兜底方案 |
|---|---|---|---|
| 认知/获取/上手/日常使用/求助/迁移离开 | | | |

- [ ] 核心体验的关键环节均为自控或有强标准约束的深度合作。
- [ ] 不可控环节都有兜底设计（默认值、异常路径、退出路径）。
- [ ] 合作方的商业激励与我方体验目标一致，不一致处有预案。
- [ ] 跨环节衔接处无"出戏点"（账号、数据、通知、支付、客服的接缝）。
- [ ] 自控范围的成本与其保护的体验价值相称，不为掌控而掌控。

**红旗**：用户在环节接缝处需要自己想办法（手动导数据、换 App、重复登录）；"这是合作方的问题"出现在核心路径上且无兜底。

## Step 5 品类定位

- [ ] 明确写出所对应的既有品类，以及用户当前的凑合方案。
- [ ] 列出既有方案最关键的痛点，且有真实用户证据（不是团队臆想）。
- [ ] 本产品对每个痛点给出端到端的消除方式，而非只在表层换形态。
- [ ] 若声称"开创全新品类"，有需求已存在的证据和用户教育成本估算。
- [ ] 用户从旧方案迁移过来的路径（数据、习惯、成本）被设计过。

**红旗**：只有"市场规模 TAM"论证，没有用户当下如何凑合的实地观察；卖点是"我们也有+我们更多"；竞品对比只比参数表。

## Step 6 工艺、情感与机制

触点清点：

| 触点类别 | 具体时刻 | 当前表现 | 评级 |
|---|---|---|---|
| 首次（下载/注册/授权/第一个空状态） | | | |
| 日常（核心任务的高频时刻） | | | |
| 异常（加载/断网/报错/权限拒绝/支付失败） | | | |
| 离开（导出/注销/退换/客服衔接） | | | |
| 不可见（内部结构、性能、隐私默认、交付质量） | | | |

- [ ] 用一个词定义了期望情绪（calm/confident/delighted/in control），关键触点都在强化它。
- [ ] 异常路径与主流程完成度一致，没有技术堆栈式报错和死胡同。
- [ ] 空状态在引导下一步，而不是显示空白或"暂无数据"。
- [ ] 等待过程有设计（进度预期、可继续操作），不白屏卡死。
- [ ] 没有为"显得有温度"而添加妨碍任务的卖萌/动效/弹窗。
- [ ] 无障碍、隐私默认值是内生设计而非事后补丁。
- [ ] 抽查任意间距/时长/文案，都能解释为什么是现在这样（无随机值）。

**决策机制（原则 10，能看到组织信息时检查）**
- [ ] 每个关键体验环节有唯一负责人（DRI），而非"某团队集体负责"。
- [ ] 离用户场景最近的人对体验有否决/裁决权，决策链不超过两级。
- [ ] 团队按端到端体验编组，不存在职能部门交接造成的体验真空。

**红旗**：只有主流程 Demo 可看，一问异常路径就卡壳；情绪表达靠吉祥物和感叹号；错误信息在责备用户（"您的操作有误"）却不给出路。

## 通用红旗信号

按证据与任务影响判定等级，不因关键词自动升级。

1. 用户需要学习产品的内部概念才能完成任务。
2. 同一个任务在不同入口有不同结果，或看起来一样的东西行为不一样。
3. 用户为系统/组织问题买单（手动同步、重复填写、自己拼接流程）。
4. 关键动作没有撤销/反悔路径，或对非破坏性操作也频繁弹确认。
5. 产品最想推的功能，出现在用户最不需要它的路径上。
6. 评审中出现"先这样，后面再优化"但说不出后面是什么时候、谁负责。
7. 任何"苹果也这样/行业都这样"式论证——要求回到用户任务本身重新论证。
