## 独立开发者的三条约束

大公司的方法论不能照抄，因为独立开发者面对的约束完全不同：

1. **时间是本金，不是人力。** 你没有下属可以并行，每多做一个功能、多维护一个依赖，都在从唯一的本金里提款。任何"以后会有用"的东西，现在都在吃掉你验证需求的时间。
2. **一个人就是整条端到端链条。** 产品、前端、后端、运维、客服全是你——原则 4 的"链条断点"在独立开发这里，断点往往是"未来的你自己"：没写日志、没做错误兜底、没留迁移路径，三个月后都是你买单。
3. **出货是为了学习，不是为了交付完美。** 独立产品最大的风险是做出没人要的东西，而不是代码不够优雅。技术决策的第一衡量标准是"它让我多快拿到真实用户反馈"。

这三条约束下，苹果原则的用法会偏向：**更快地砍、更晚地抽象、只在核心体验处自控。**

## 十条原则的工程映射

### 1. 一句话定义 → 每个模块只解决一个任务

- 每个模块/类/API endpoint 用一句话说清职责；一句话里出现不同职责时，检查是否需要拆分；共享事务或任务可保留一起。
- 命名描述调用方要完成的任务（`cancelSubscription`），而不是内部实现（`setStatusTo3`）。
- **检查问题**：新人（或三个月后的你）只看函数名，能猜对它做什么和不做什么吗？
- **Slop**：`Manager`、`Helper`、`CommonUtil` 这类什么都能装的名字，本质是没想清职责。

### 2. 聚焦说不 → 依赖、配置、抽象的减法

- 每引入一个依赖都要回答：它服务的核心任务是什么？删掉它我要多写多少代码？该依赖的维护风险谁承担？
- 配置项/功能开关从 0 开始长：先提供合理默认值；安全、部署差异或已确认需求需要的配置提前保留。
- **检查问题**：这个抽象是第三个重复出现时才提炼的，还是我预判"以后会需要"？（三次重复是启发式提醒；按需求稳定性、安全边界和迁移成本判断）
- **Slop**：为了"灵活"预留的插件机制、策略模式、配置矩阵——未经需求验证的扩展点可能闲置，却持续增加维护成本。
- **动作**：列依赖/抽象清单，逐个标注 保留 / 用标准库替代 / 删除。

### 3. 体验倒推技术 → 先写调用方，再定实现

- 先写调用代码（call site）和用户使用故事，倒推接口签名、数据模型、状态流转，而不是先建表再想怎么暴露。
- API 设计从"一个典型请求长什么样"开始，而不是从数据库 ER 图开始。
- **检查问题**：是实现的方便决定了接口形状，还是调用方的体验决定的？
- **Slop**：把数据库表直接序列化当 API 返回；为了 ORM 好写让前端承担数据拼装。

### 4. 端到端负责 → 依赖链与"未来的你"兜底

- 画出一次核心请求的完整链路：你的代码 → 框架 → 第三方 API → 支付/邮件/存储 → 网络。逐环标注：它失败时用户看到什么？
- 独立开发者的端到端不是什么都自建，而是**对每个不可控环节设计兜底**（超时、重试、降级、明确报错），并在"是不是核心体验"处决定是否自控。
- **检查问题**：第三方服务宕机时，你的产品是优雅降级，还是直接白屏？半夜告警谁处理——有没有让它根本不需要半夜处理的设计？
- **选型准则**：核心体验环节优先自控或选最可靠方案；非核心环节默认托管（见下方买/租/建）。
- **Slop**：只写 happy path，假设第三方永远可用、网络永远通畅、用户永远按流程输入。

### 5. 重定义品类 → 做 devtool/模板/API 产品时同样适用

- 如果你做的是开发者工具、SDK、模板、脚手架：先找现有工具最影响主任务的关键点（配置繁琐、文档缺失、默认值反人类），端到端重做，而不是再做一个"功能更多"的同类。
- **检查问题**：你的 devtool 让"5 分钟跑通第一个结果"成为可能了吗？

### 6. 深层简洁 → 复杂度封在内部，绝不泄漏给调用方

- 好的抽象把复杂吃掉，调用方只看到简单接口；坏的抽象只是把复杂度换个地方推给用户（泄漏实现细节、要求理解内部状态机）。
- 给聪明的默认值，高级能力分层渐进披露：简单路径零配置，复杂路径才出现选项。
- **检查问题**：用户完成最常见的任务需要几行代码/几次点击？每多一步，是在为他解决问题，还是在为你的架构买单？
- **Slop**：把"灵活"当卖点，让用户填 8 个配置才能开始；本质是把设计工作转嫁给用户。

### 7. 工艺细节 → 四态完整、错误可行动、柜子背面

- 每个界面和接口补齐四种状态：**空 / 加载中 / 正常 / 错误（含超时）**，缺任何一个都是半成品。
- 错误信息必须可行动：说清发生了什么、用户下一步做什么；面向用户的错误不暴露堆栈，面向自己的日志要够定位问题。
- "柜子背面"= 日志、数据校验、迁移脚本、README、异常路径——没人看，但出事时决定你多快能修好。
- **检查问题**：断网、权限被拒、支付失败、重复提交、数据为空时，产品分别是什么表现？
- **Slop**：主流程 demo 完美，一问异常路径就是"后面再处理"。

### 8. 技术×人文 → 开发者体验也是产品体验

- 即使你的用户是普通用户，你自己（和未来的协作者/AI 编程助手）也是这个代码库的"用户"：清晰命名、最小启动步骤、一条命令跑起来本地环境。
- 面向开发者的产品（API/CLI/SDK）：上手情绪曲线要在 5 分钟内给一次成功体验；报错的语气、文档的第一个例子，决定别人留下还是关掉。
- **检查问题**：换台电脑，照着 README 能在 15 分钟内跑起来吗？

### 9. 原型先于论证 → spike 裁决架构分歧

- 架构选型有分歧时，花半天写最小 spike 验证关键假设（性能、集成难度、开发体验），用结果决策，不在文档里辩论。
- 独立开发者更要防止"准备式拖延"：一直在搭基建、换框架、重构，就是不发布。
- **检查问题**：这个技术决策错了的代价多大、多快能改？可逆的快速决定，不可逆的才慎重（见下方双向门）。
- **动作**：为最高优先级且资源可覆盖的技术风险各写一个 spike，写清通过/放弃标准和时间盒（如半天）。

### 10. 品味决策机制 → 你就是 DRI，别用"最佳实践"逃避决定

- 独立开发没有委员会，但常见的逃避是"业界都这么做/这个框架最火"——这是把品味决策外包给潮流。
- 每个技术选型写一行理由：它解决我这个产品的什么具体问题。写不出就是简历驱动开发（用新技术给自己镀金）。
- 为每个模块指定唯一 owner——永远是你，但要明确"这块以后谁改、按什么标准改"，避免三个月后自己都不敢动。

## 买 / 租 / 建：独立开发者的选型顺序

端到端原则在资源有限时的正确展开：

| 选项 | 含义 | 默认选择条件 |
| --- | --- | --- |
| 买（SaaS/托管） | 用现成服务（托管数据库、认证、支付） | 非核心环节、验证期——默认选这个，换上线速度 |
| 租（开源/框架） | 用成熟开源方案自部署 | 需要可控但不值得自研 |
| 建（自研） | 自己写 | 核心体验、数据驻留、安全、可靠性或迁移成本有明确依据时 |

**自研需要明确依据**：核心体验、数据驻留、可靠性、安全或迁移成本均可能构成理由。验证期通常优先现成方案，但遵守用户的技术与采购约束。

**双向门检查**（决策可逆性）：可逆决策（双向门）快速定、先做再说；不可逆决策（数据模型、加密、收费模式、数据删除策略）放慢，写清后果再动手。

## 开工前轻量评审清单

不是大厂 RFC 流程，是独立开发者开工前 30 分钟的自检。括号内为对应原则。

**本质与边界**
- [ ] 这次开发服务哪个具体用户任务？一句话说清（1）
- [ ] 范围里哪些是"顺手也做了"的？划掉（2）
- [ ] 不做什么是否已写明（2）

**接口与抽象**
- [ ] 先写了调用方代码/使用故事，再定的接口（3）
- [ ] 最常见路径零配置或近零配置，复杂度封在内部（6）
- [ ] 提前抽象有明确需求依据；不单凭“三次重复”决定（2）
- [ ] 命名描述任务而非实现（1）

**依赖与选型**
- [ ] 每个新依赖都有一行"为什么非它不可"，且知道它挂了怎么办（2、4）
- [ ] 按采购、离线、安全和数据约束决定托管或自建（4、买租建表）
- [ ] 不可逆决策已单独标注并想过后果（双向门）

**状态与兜底**
- [ ] 空/加载/正常/错误（含超时）等相关状态都有设计（7）
- [ ] 第三方失败有降级路径，错误提示可行动（4、7）
- [ ] 关键路径有最小日志，出问题能定位（7）

**出货与验证**
- [ ] 这个版本能多快拿到第一个真实用户反馈？（约束 3）
- [ ] 最大的技术假设是否有时间盒内的 spike 验证（9）
- [ ] 有没有在为"上线后再说"的规模做提前优化？有就删（2、9）

## 独立开发者反模式

| 反模式 | 表现 | 对应原则的纠正 |
| --- | --- | --- |
| 技术玩具陷阱 | 选新技术是因为想学/它很酷，产品需求反而是凑的 | 体验倒推：先有要解决的体验，技术只是手段（3） |
| 准备式拖延 | 反复换框架、搭脚手架、重构，迟迟不发布 | 原型与出货：架构服务于学习速度（9、约束 3） |
| 镀金 | 核心没验证，先把后台管理、暗色模式、i18n 全做了 | 聚焦：先检查核心任务影响；没有数据不假设用户比例（2） |
| 简历驱动开发 | 选型以"写在简历上好看"为标准 | 每个选型写解决的具体问题（10） |
| 假设规模焦虑 | 还没用户就为十万并发设计微服务 | 可逆决策快速做，规模问题等证据（9、双向门） |
| happy path 交付 | 异常状态全留 TODO，上线即裸奔 | 四态与兜底是工艺底线（7） |
| 失控的自建 | 认证/支付/邮件全自研，三个月没上线 | 买租建：按体验和用户约束说明自研必要性（4） |
| 功能蔓延 | 每天加一个"用户可能需要"的功能，没有 not-doing list | 显式拒绝清单，对好主意说不（2） |
